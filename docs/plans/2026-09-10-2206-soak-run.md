# Soak Run Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `bb soak` gate that drives one long-lived server through many rounds of realistic file churn on a pinned real corpus, and fails when the index stops agreeing with a freshly started server, when memory grows across identical states, or when any request stops answering.

**Tech Stack:** Rust (`tests/test_soak.rs`, the shared `LspClient` in `tests/common/`), babashka (`bb.edn`), the corpora already pinned by `bb bench`. No server changes.

---

## Design

### Why

`bb check` proves the server is correct on fixtures that never change under it. `bb bench` proves it is fast for the first two minutes of a session. Neither covers the shape of a real working day: hundreds of edits, saves, file creations and deletions, branch switches, all against one process that has been up for hours. The failures that live there are index corruption after churn, memory that never comes back, and a handler that stops answering — none of which the current gates can see.

### The oracle problem, and the answer

After arbitrary churn there is no way to know the right answers by construction. So the soak does not try. At each checkpoint it brings the churned server to a quiesced, known on-disk state, starts a **fresh reference server** on that same state, and requires the two to answer identically over a fixed probe set. A cold server is the reference implementation. On the clj-kondo corpus it starts in about half a second, so this is affordable every round.

This subsumes an index-accounting check: duplicate or stale entries show up as differences in `workspace/symbol` results against the reference.

### Oracles

1. **Liveness**, continuously: every request returns within its timeout and without a JSON-RPC error, the process is still alive (`Child::try_wait`), and the accumulated `.clj-pulse/server.log` record never contains `panicked at`. The panic hook logs through `tracing::error!` and the default level is `WARN`, so the log line appears without `--verbose`; the error-response half of the check exists because the reference server truncates that log (see *Panic evidence*).
2. **Differential correctness**, per checkpoint: churned server vs reference server over the probe set. Any difference fails the run and prints both answers.
3. **Convergence**, per churn batch: after each batch the server must come to reflect the new on-disk state within a deadline. Failing to converge is a real bug (a watched change that was dropped), so the deadline fails the run.
4. **RSS drift**, per checkpoint: sampled at the same quiesced, all-closed, baseline-on-disk state, so the samples are comparable. Fails when the last checkpoint exceeds the first by more than `SOAK_RSS_GROWTH` (default 1.5x) — generous enough not to flake on allocator behaviour, tight enough to catch a leak.
5. **Latency drift**, per checkpoint: definition median at the first and last checkpoint. Reported, never fails: too noisy to gate on.

### Convergence, and why not a log wait

`did_change_watched_files` logs per file at `info!` and pushes nothing to the client, so there is no client-visible "reindex finished" signal, and turning on `--verbose` to tail one would change the workload being measured. Instead every churn action carries a **witness**: a `workspace/symbol` query whose answer must change as a direct consequence of that action. `workspace/symbol` is the right vehicle because `workspace_symbols(index, query)` reads the index alone — no document has to be open — and it matches on symbol *name*.

That last detail decides the design. A query cannot select on namespace or path, so "no `soak_` symbol exists" is not a query anyone can write. Instead **every churn action introduces or removes a uniquely named var**:

- a `Create` writes `(defn soak-witness-<seed>-<round>-<n> [] nil)` into the new namespace; it converges when a query for that exact name returns exactly one result at the expected path;
- a `Delete` converges when the query for its var returns nothing;
- a `ModifyOnDisk` *appends* such a def, so a modification is witnessed the same way a creation is;
- a `Rename` is witnessed on both sides: the same var name, at the new path, and no result at the old one.

Every action in a batch is witnessed, not one action per batch — a bulk round that converges for its first file and drops its ninetieth is exactly the bug worth catching, and 100 index-only queries are cheap. The driver polls every 100 ms until all of a batch's witnesses converge, or `SOAK_CONVERGE_TIMEOUT` (default 30 s) passes and the run fails, naming the actions that never landed.

`workspace/symbol` truncates at 128 results, which never affects a witness (a unique name returns one). It does affect the comparison queries in the probe set, so those are chosen at probe-selection time by asking the reference server and keeping only queries whose result count is well under the cap — a truncated list is not a set two servers must agree on.

### The churn model

Deterministic and seeded. A small LCG in the test file (no new dependency); `CLJ_PULSE_SOAK_SEED` is printed on every run, so any failure replays exactly.

```rust
/// One churn action. `OnDisk` variants are always paired with a
/// `didChangeWatchedFiles` notification; `Buffer` never touches disk.
enum Edit {
    /// Type at the end of an open buffer: didChange only, no disk write.
    Buffer { file: PathBuf },
    /// Write the open buffer's current text to disk, then didSave.
    Save { file: PathBuf },
    /// Rewrite a tracked corpus file on disk (append a form), notify Changed.
    ModifyOnDisk { file: PathBuf },
    /// Write a new namespace file the soak owns, notify Created.
    Create { file: PathBuf, ns: String },
    /// Remove a file the soak created, notify Deleted.
    Delete { file: PathBuf },
    /// Delete + Create with the ns renamed to match the new path.
    Rename { from: PathBuf, to: PathBuf, ns: String },
}
```

Every round draws a mix of these. Every `SOAK_BULK_EVERY`-th round (default 5) is a **bulk** round: at least `SOAK_BULK_FILES` (default 100) files churned and delivered in a *single* `didChangeWatchedFiles` notification, which is the shape a branch switch has from the server's point of view. That is why the plan does not fetch a second commit per corpus: a real switch costs another full shallow tree fetch (cheap for clj-kondo, not for metabase) and delivers nothing the oracle needs, since the reference server works against whatever is on disk.

Files the soak creates live under `<corpus>/src/soak_<seed>/` and are named so they cannot collide with corpus files. Modifications to tracked files only ever *append* a form, so a corrupted parse cannot be blamed on the churn generator.

### Restoring the corpus

The soak churns the corpus checkout in place. A `CorpusGuard` with a `Drop` impl restores it — `git checkout -- .` for tracked files, plus removing the `src/soak_<seed>/` tree — so a panic or a failed assertion still leaves the checkout at its pinned commit. `bench-corpus!` re-pins on the next `bb bench`/`bb soak` anyway, which is the second line of defence. The alternative, a copy or a `git worktree`, costs a duplicate metabase tree and a second dependency resolution for no gain on a disposable `.tmp/` checkout.

`git checkout -- .` is deliberate: `git clean -fd` would delete the bench's caches (`.clj-pulse/jar-cache`, `.lsp/`) which are not in metabase's `.gitignore`, and re-earning those costs minutes.

### The checkpoint procedure

Every `SOAK_CHECKPOINT_EVERY` rounds (default 5), and always after the last round:

1. `didClose` every open document, dropping all unsaved buffer state.
2. Restore disk to baseline (`git checkout -- .`, remove the soak's own tree).
3. Send one `didChangeWatchedFiles` covering everything restored.
4. Poll the baseline witnesses until converged (below).
5. Quiesce: no `window/logMessage` for 2 s and no child process of the server (the same rule `bb bench` settles on).
6. Sample RSS here, with no documents open — the only state in which two checkpoints are comparable.
7. Snapshot `.clj-pulse/server.log` (see *Panic evidence*), then start the reference server and settle it.
8. `didOpen` the probe files, from the on-disk text, on **both** servers.
9. Run the probe set against both, compare, time 20 definitions on the churned server, kill the reference.

Steps 1-3 are what make the comparison fair: the reference server has no open buffers and no unsaved edits, so the churned server must be brought to the same footing first.

Step 8 is not optional and is easy to get wrong. `textDocument/definition` resolves through `DocumentStore` at every branch — `local_definition` and `resolve_fqn_at` both take a `snapshot`, and the bare-word path needs `word_at` — and `documentSymbol` reads a snapshot too. With no document open, all of them answer `null` on *both* servers, and the comparison passes while testing nothing. So the probe files are re-opened from disk after the RSS sample, on both servers, and the run fails if a definition probe that is supposed to resolve comes back null on the reference: a probe set that answers nothing is a broken oracle, not a passing one.

**Reference readiness is the settle rule, not the `Indexed` line.** Library indexing and stage-3 classpath resolution run after stage 1, and the bench already records that sampling at `Indexed` folds a background reindex into everything after it. The reference server must reach the same settled state the churned server is held to (stage-3 line, no child process, 2 s quiet) or the comparison invents divergences. This is what makes a checkpoint expensive on metabase — roughly 50 s, most of it the clj-kondo dependency-cache warm — so `SOAK_CHECKPOINT_EVERY` defaults higher for that corpus.

### Panic evidence

`main.rs` opens the log with `File::create`, which truncates, and the log path is derived from the working directory — which both servers share. So every reference-server start wipes the churned server's `server.log`. Two consequences the driver has to handle:

- The churned server's log is read and appended to an in-memory record **before** each reference start, and the panic check runs against that record, not against whatever the file holds at the end.
- A panic inside a request handler also comes back as a JSON-RPC error response, because `PanicGuard` answers that one request with an internal error. The driver treats *any* error response as a liveness failure, which catches handler panics independently of the log.

### The probe set

Reuse the bench's site discovery (`tests/test_bench.rs`'s rules: a `src`/`test` file, a namespace-to-file match anchored at the source root, a target file that really defines the name), because those rules were tuned to pick sites either server can actually answer. The probe set is:

| Request | Compared how |
|---|---|
| `textDocument/definition` at N sites | Exact equality, and at least one must resolve non-null |
| `textDocument/references` at N sites | Equality as a sorted set of (uri, range) |
| `textDocument/documentSymbol` on N files | Exact equality |
| `workspace/symbol` for N fixed queries | Equality as a sorted set |
| `textDocument/completion` at N sites | Liveness only: answers, no error |
| `textDocument/hover` at N sites | Liveness only |

Completion and workspace-symbol *ranking* depend on occurrence counts, and completion is explicitly `isIncomplete`, so equality on ordering would flake. Completion is checked for liveness; `workspace/symbol` is compared as a set, which is stable, rather than as a list.

### Settings

All environment variables, all read once at startup and echoed in the report header, so a run is reproducible from its own output.

| Variable | Default | Meaning |
|---|---|---|
| `CLJ_PULSE_SOAK_ROOT` | set by `bb soak` | the corpus checkout |
| `CLJ_PULSE_SOAK_CORPUS` | set by `bb soak` | corpus name, for the report |
| `CLJ_PULSE_SOAK_SEED` | random, always printed | replays a failing run exactly |
| `CLJ_PULSE_SOAK_ROUNDS` | 20 | churn rounds |
| `CLJ_PULSE_SOAK_FILES` | 10 | files churned per ordinary round |
| `CLJ_PULSE_SOAK_BULK_EVERY` | 5 | rounds between bulk (branch-switch shaped) rounds |
| `CLJ_PULSE_SOAK_BULK_FILES` | 100 | files in one bulk batch, one notification |
| `CLJ_PULSE_SOAK_CHECKPOINT_EVERY` | 5 on clj-kondo, 10 on metabase | rounds between checkpoints; a metabase checkpoint costs ~50 s because the reference server has to settle |
| `CLJ_PULSE_SOAK_CONVERGE_TIMEOUT` | 30 s | a batch that has not landed by then fails the run |
| `CLJ_PULSE_SOAK_RSS_GROWTH` | 1.5 | last checkpoint over first, above which the run fails |
| `CLJ_PULSE_SOAK_PROBES` | 12 | sites per request kind in the probe set |

### Scale and runtime

`bb soak` defaults to the clj-kondo corpus and 20 rounds, which is a few minutes. `bb soak metabase` is the long one. `CLJ_PULSE_SOAK_ROUNDS` overrides. Like `bb bench` the test is `#[ignore]`d, so `cargo test` never picks it up, and unlike `bb bench` it is a gate: it exits non-zero when an oracle fails.

### Non-goals

- **No config churn, and no `deps.edn` churn.** Editing `deps.edn` triggers real dependency resolution and network, which would make the run non-hermetic. `.clj-pulse/config.edn` and `.clj-kondo/config.edn` were in scope in the first draft and are dropped: both are gitignored, so `git checkout -- .` would not restore them and the guard would need a second restore path, and each needs a reload witness of its own rather than the uniform `workspace/symbol` one. Worth a follow-up once the tool has earned its keep; not worth a second restore hazard in v1.
- **No new server method for index counts.** An index-statistics endpoint would make the accounting check direct, but the differential oracle already exposes duplicates and stale entries through `workspace/symbol`. Revisit only if the oracle proves too coarse in practice.
- **No concurrency fuzzing.** One client, requests in order. Racing requests against churn is a separate tool.
