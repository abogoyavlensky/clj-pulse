**Status: completed** (2026-09-05)

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `bb e2e-pulse`, a headless end-to-end gate that drives clj-pulse through the real Clojure Pulse VS Code extension, and add a docs accuracy step to the release flow (ROADMAP Milestone 0).

**Tech Stack:** Node (`@vscode/test-electron`), Xvfb, VS Code, the Clojure Pulse extension (`../clojure-pulse-vscode`, packaged with `@vscode/vsce`), babashka tasks. No Rust changes.

## Design

### Why

Clojure Pulse is the first-priority editor, yet the only VS Code gate today is Calva (`scripts/calva-e2e/`). The two clients differ where it matters: Clojure Pulse talks to the server through vscode-languageclient directly and serves `jar:` documents by calling the server's `clojure/dependencyContents` request, while Calva reads JARs itself and only needs correct `jar:` locations. A server change can break one without the other.

### Shape

A new `scripts/pulse-e2e/` harness mirrors `scripts/calva-e2e/` file for file:

- `runner.js` copies the fixture to a temp dir, generates `.cpcache` with `clojure -Spath`, writes workspace settings pointing `clojurePulse.server.path` at `target/debug/clj-pulse`, downloads VS Code, installs the Clojure Pulse `.vsix`, and runs `tests.js` inside the extension host.
- `tests.js` runs six checks through public VS Code commands, polling each with a deadline, collecting failures and reporting them together, and throws at the end if any failed.
- `bb e2e-pulse` builds the debug binary and runs the harness under `xvfb-run`.

### VSIX acquisition, in order

1. `CLJ_PULSE_VSIX` environment variable, if set: used as-is.
2. Sibling checkout `../clojure-pulse-vscode` (resolved from the harness dir as `../../../clojure-pulse-vscode`), if it has a `package.json`: package it with `npx vsce package -o <target>` run in that directory, after `npm ci` when `node_modules` is missing. The target is `scripts/pulse-e2e/.vscode-test/clojure-pulse-<version>-<short sha>.vsix`; it is rebuilt when the file is missing or the extension's working tree is dirty (`git status --porcelain` non-empty), so a clean HEAD is packaged once and an edited tree is packaged every run.
3. Otherwise the latest GitHub release: read `https://api.github.com/repos/abogoyavlensky/clojure-pulse-vscode/releases/latest`, take the asset whose name ends in `.vsix`, download it once to `.vscode-test/clojure-pulse-release.vsix`.

The runner prints which source it used.

### Checks

The fixture is a deps.edn project with `org.clojure/data.json` and three source files (see File Structure). Positions are found by searching for a needle in the document text, as the Calva harness does.

1. **Extension present and active.** `vscode.extensions.getExtension("abogoyavlensky.clojure-pulse")` exists; activate it. The `workspaceContains:**/deps.edn` activation event normally does this already.
2. **Project definition.** `vscode.executeDefinitionProvider` on `o/helper` in `src/app.clj` returns a location whose path ends in `/src/other.clj`. This is also the indexing wait: poll up to 60 s.
3. **Library definition and `jar:` content.** Definition on `json/write-str` returns a location with scheme `jar`. `vscode.workspace.openTextDocument(jarUri)` yields text containing `(defn write-str`, and the location's start line contains `write-str`. Opening the document goes through the extension's own content provider, which calls `clojure/dependencyContents`.
4. **Hover.** `vscode.executeHoverProvider` on `o/helper` returns contents including the docstring `A project-internal helper.`
5. **Completion.** `vscode.executeCompletionItemProvider` at the position just after `o/he` inside the `o/helper` token returns an item whose label (or `label.label`) contains `helper`. Check `src/handlers/completion.rs` for the exact label shape of alias-qualified items before asserting.
6. **Diagnostics.** Open `src/lint.clj`, which requires `clojure.set` and never uses it. Poll `vscode.languages.getDiagnostics(uri)` up to 60 s for a diagnostic whose code is `unused-namespace` (the code may be a string or `{ value }`). Assert on the code only: with clj-kondo installed (it is, via mise) the source is `clj-kondo`; without it the source is `clj-pulse`. Both are correct behavior.

Not checked, deliberately: `clojurePulse/ignoredForms`. VS Code has no API to read decorations, so the dimming cannot be observed from the extension host. `bb e2e` covers the request and the extension's unit tests cover the decorator.

### Shared VS Code download

Both VS Code harnesses download VS Code into one cache, `scripts/.vscode-cache/`, passed as `cachePath` to `downloadAndUnzipVSCode`. Each harness keeps its own `.vscode-test/` for the extensions dir, user-data dir, and cached `.vsix`, and passes `--user-data-dir` and `--extensions-dir` explicitly in `launchArgs` so the two never share state. The Calva runner gets the same `cachePath` (a one-line change) and its already-downloaded VS Code is moved into the shared cache.

Check the installed `@vscode/test-electron` signature before wiring `cachePath`: in 2.4 `downloadAndUnzipVSCode` accepts an options object `{ version, cachePath }`.

### Real conditions

No `CLJ_PULSE_DISABLE_*` variables. The server sees the mise-installed `clojure` and `clj-kondo` exactly as it would on a user's machine.

## Completion summary

`bb e2e-pulse` is in place: `scripts/pulse-e2e/` packages the sibling
`../clojure-pulse-vscode` checkout (falling back to `$CLJ_PULSE_VSIX`, then the
latest GitHub release), installs it into a real VS Code under Xvfb with
`clojurePulse.server.path` pointed at `target/debug/clj-pulse`, and runs six
checks through public VS Code commands: extension activation, project
definition, `jar:` navigation plus content served by the extension's
`clojure/dependencyContents` provider, hover, completion, and the
`unused-namespace` diagnostic. Both VS Code harnesses now share one VS Code
download (`scripts/.vscode-cache/`) while keeping separate extension and
user-data dirs. Docs name the gate and the right request throughout, and
`docs/RELEASE.md` gained a docs accuracy sweep before tagging. Both Milestone 0
items are ticked.

Final verification: `bb check` (110 tests), `bb e2e`, `bb e2e-nvim`,
`bb e2e-pulse` (9 ok lines), `bb e2e-calva` all pass.

### Deviations

- `CLJ_PULSE_E2E_NO_LOCAL=1` kept as a documented switch in the runner header
  rather than removed — it is how the release fallback stays verifiable.
- The placeholder `tests.js` was committed with the runner so HEAD stayed
  runnable between Task 2 and Task 3.
- `resolveCliArgsFromVSCodeExecutablePath` injects its own `--extensions-dir` /
  `--user-data-dir` under the default cache path; both runners filter them out
  instead of relying on VS Code's last-wins.
- Nothing was moved into the shared VS Code cache. `version: "stable"` resolves
  to 1.136.1 while Calva's own copy was 1.135.0, so the first `bb e2e-pulse`
  populated the shared cache and Calva reuses it; moving the stale copy would
  only have added dead weight.
- Codex review found three ways the runner could pass against the wrong
  extension (a dirty build cached at the clean-HEAD path, a downgrade VS Code
  silently refuses, an ignored install exit status) and one fresh-checkout
  break in the Calva runner (`.vscode-test/` was created by the download that
  now goes elsewhere). All four are fixed; the Calva fix was verified by
  running the gate with that directory moved aside.

### What the plan could have specified better

The plan told the runner to install the `.vsix` but not to prove the install
took effect — no `--force`, no exit-status check, no separate artifact for a
dirty build. For a gate whose entire value is "the extension you built is the
one under test", those belonged in the design rather than in review. It also
assumed the Calva download would keep creating `scripts/calva-e2e/.vscode-test/`
after `cachePath` moved the download elsewhere, and prescribed a one-time `mv`
of a VS Code copy that turned out to be a stale version.
